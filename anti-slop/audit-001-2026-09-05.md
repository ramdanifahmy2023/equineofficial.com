2. **[P1] Refresh dan perubahan keranjang mengubah detail invoice yang sama.**

   Lokasi: [payment, baris 8](</home/ubuntu/Sites/Equine stagging/pages/payment/[orderNumber].vue:8>) dan [checkout, baris 49](</home/ubuntu/Sites/Equine stagging/pages/checkout.vue:49>).

   Reproduksi terkonfirmasi: beli Carpenter Rp257.500, pilih J&T Rp20.000 dan BRI VA. Halaman pembayaran menunjukkan Rp277.500. Refresh URL yang sama: metode berubah menjadi QRIS, pengiriman menjadi JNE Rp18.000, dan total menjadi Rp275.500. Setelah tombol sukses ditekan, item hilang dan subtotal menjadi Rp0; dalam rangkaian ini total turun menjadi Rp18.000. Refresh berikutnya mengembalikan status menjadi pending.

   Penyebab: `checkout-draft` dan status hanya berada di memori, sedangkan item invoice membaca keranjang aktif. Tidak ada snapshot berdasarkan nomor order. Query `method` tidak memulihkan metode.

   Perbaikan: buat mock repository order berdasarkan nomor order dengan snapshot item, kontak, pengiriman, total, dan status; render invoice dari snapshot tersebut. Tetapkan penanganan nomor order yang tidak ditemukan. Backend kelak menggantikan mock repository itu. Rujukan: R-27, state invoice tidak bertahan pada refresh.

**Kesiapan produksi di luar bug frontend**

Dokumen rencana secara eksplisit membekukan backend dan provider sampai frontend disetujui. Karena itu, ketiadaan berikut dicatat sebagai pekerjaan tahap selanjutnya, bukan regresi backend:

- Belum ada API order, pembayaran, webhook Pakasir, atau ongkir RajaOngkir. Checkout memakai empat tujuan dan tiga tarif tetap.
- Admin dapat dibuka tanpa login, tetapi isinya data mock. Autentikasi dan otorisasi server diperlukan sebelum data nyata atau operasi admin dihubungkan.
- Harga, stok, varian, serta status aktif admin belum menjadi sumber data bersama dengan storefront. Dibutuhkan validasi server dan pengelolaan stok sebelum menerima pesanan nyata.
- Kebijakan retur, size chart, origin gudang, berat varian, dan informasi provider masih memerlukan data resmi.

Prioritas pengerjaan yang disarankan: nomor 1–3 terlebih dahulu, kemudian nomor 4–8, lalu nomor 9–10 sebelum persetujuan frontend. Audit tidak mengubah atau memperbaiki temuan tersebut.

**Batas pemeriksaan**

Pemeriksaan browser memakai dev server lokal yang sudah berjalan; build produksi diuji terpisah. Hasil bukan audit domain publik, penetration test, audit dependency/CVE, sertifikasi aksesibilitas penuh, atau pengukuran Lighthouse/Core Web Vitals. Kondisi layout yang lulus hanya mencakup rute dan ukuran layar yang dicatat, bukan seluruh variasi konten, zoom, atau perangkat.
